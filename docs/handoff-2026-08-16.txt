WHAT HAPPENED THIS SESSION, IN ORDER

This session picked up after a large prior rename (Forge -> ForgeStack) and
credential setup had already landed. The work here was: get a real human
through login and GitHub App install for the first time ever, and fix
whatever broke. Four real, previously-invisible bugs were found and fixed,
entirely by actually running the app rather than trusting the test suite -
this is a recurring theme in known-gaps.md and worth internalizing before
touching this code: the test suite runs everything against Testcontainers
with overridden config and has NEVER booted the packaged application the way
a user actually runs it. That gap is explicitly still open (see
known-gaps.md, section 5, "No test boots the packaged application" - marked
the highest-value gap in the whole document).

Bug 1 (commit 6234e78) - the OAuth servlet session shadowed the ForgeStack
session. oauth2Login's default SecurityContextRepository persisted the
OAuth2AuthenticationToken into the servlet session; SecurityContextHolderFilter
restored it on every later request; ForgeStackSessionAuthenticationFilter was
guarded on "no authentication present" so it never read the actual ForgeStack
cookie at all. Result: every one of the seven @AuthenticationPrincipal
endpoints NPE'd with a 500 the moment a real browser (which holds a servlet
session cookie AND the ForgeStack cookie at once) tried to use them. curl never
caught this because curl does not carry a servlet session unless you make it.
Fixed with NullSecurityContextRepository, deleting the filter's guard entirely
(not inverting it - "cookie takes precedence" would have silently broken
session revocation), and requiring a ForgeStackPrincipal specifically at the
authorization layer instead of just authenticated(). Also found and fixed
along the way: GitHub's user access token was being retained forever in
Boot's autoconfigured InMemoryOAuth2AuthorizedClientService, contradicting the
plan's explicit claim that no user token is persisted. New class
DiscardedGithubUserTokens throws it away on write. Test:
LoginSessionIntegrationTest, six of seven assertions watched failing first
against the real bug before the fix landed.

Bug 2 (commit 0c2b542) - the GitHub App setup nonce was bound to a session id,
and its rejection reason was unreadable. The install flow spans GitHub's own
install screen, which takes minutes; a session churn in that window (re-login,
or in the user's actual case, switching Chrome profiles/GitHub accounts mid
test) meant the nonce no longer matched by the time the callback arrived.
Fixed by binding the nonce to the USER instead of the session (this is a
real, deliberate loosening - "same human, different session" was never the
threat the nonce defends against; account substitution is caught separately
by the GitHub-identity ownership check, which was untouched). Also: the single
rejection reason INVALID_SETUP_STATE covered four different causes (missing,
expired, replayed, wrong session) with one log line and one audit row - split
into SETUP_STATE_EXPIRED and SETUP_STATE_FOREIGN so an operator can actually
tell a stale link apart from a real CSRF attempt. Also: the callback endpoint
was returning an empty body on rejection, which a real browser renders as a
blank "This page is not working" - it now returns a readable text/plain
explanation.

Bug 3 (commit d098409) - same class of bug as Bug 1's symptom, on the other
side of the flow. forgestack.security.login-success-redirect defaulted to "/"
and nothing serves "/", so a SUCCESSFUL login rendered a Whitelabel 404,
indistinguishable from a failure - reported as a failure three times before
anyone realized it was actually the success path. Fixed the default to
/api/session (proof it worked, plus which GitHub account you are signed in
as - important because the install flow only accepts an installation owned by
the SAME GitHub account you are logged into ForgeStack with). The identical
mistake existed on forgestack.github.app.setup-redirect (also defaulted to
"/"), found the same way after the nonce fix: a genuinely successful install
bound correctly (confirmed via an INSTALLATION_BOUND audit row) and then hit
the same blank 404. Fixed its default to /api/repositories.

Bug 4 (not a code bug, a confirmed-live instance of an already-documented gap,
commit a52ab9b) - during testing, the user uninstalled and reinstalled the
GitHub App twice on the same account. GitHub issues a brand new installation_id
every time, and ForgeStack has no webhook handler (that is Phase 6 work,
not built yet) to notice that the OLD installation_id is now dead. Result: two
live-looking github_installations rows for the same account, each with its own
synced copy of the same 9 repositories - 18 rows for 9 real repos, and
GET /api/repositories could not tell them apart. This is known-gaps.md section
3.2 ("Uninstalls and suspensions are not noticed"), now confirmed concretely
rather than theoretically. Cleaned up by hand this session (deleted the stale
github_installations row, which correctly cascades to github_repositories and
managed_repositories via ON DELETE CASCADE - confirmed via pg_constraint before
deleting, nothing was lost since managed_repositories was empty at the time).
NOT fixed in code - see the open question below, this is unresolved.

Question 1: "Are you sure the duplicate-repository bug should be deferred to
Phase 6?"

My working answer, reached mid-investigation: probably NOT fully correct as
originally stated. What I found before being cut off:

  - The unique constraint on github_repositories is
    UNIQUE (github_installation_id, github_repo_id) - scoped per installation,
    not per workspace. Confirmed by reading
    src/main/resources/db/migration/V2__github_app.sql directly. This means
    the database will happily accept two rows for the same real GitHub repo as
    long as they hang off two different installation rows, regardless of
    whether webhooks exist.

  - RepositorySyncService.available() (the method backing
    GET /api/repositories) queries
    findByWorkspaceIdAndRemovedAtIsNullOrderByFullName(workspaceId) - it
    dedupes nothing across installations. Every non-removed repository row
    for the workspace is returned, full stop.

  - RepositorySyncService.sync(workspaceId, installationId) only reconciles
    the ONE installation it is told about. It has no way to know a
    DIFFERENT installation row for the same workspace has gone stale, because
    it only ever sees repositories.findByGithubInstallationId(installation.getId())
    for the installation it was called with.

  - I had NOT yet checked whether github_installations even has
    suspended_at / deleted_at columns in the actual schema (the plan document
    mentions them as intended columns, but I did not verify the real migration
    file), nor whether any code path currently sets them.

The real implication: even once Phase 6 webhooks exist and correctly mark an
old installation as deleted, that alone does NOT fix the duplicate-listing
problem unless something ALSO teaches available() (or the webhook handler
itself) to exclude repositories belonging to a deleted/suspended installation,
not just individually-removed repositories. Marking the installation dead and
filtering the repository list are two separate pieces of work, and only the
first one is unambiguously "wait for the webhook." The second one - fixing
available() to filter by installation status, or tightening the unique
constraint to (workspace_id, github_repo_id) so duplication cannot even be
inserted regardless of webhook timing - could arguably be done NOW,
independent of Phase 6, as a data-integrity fix rather than an
event-plumbing fix.

Next agent should: read github_installations' actual columns
(V2__github_app.sql), decide whether a workspace-scoped uniqueness fix belongs
in this session's scope or genuinely waits, and update known-gaps.md section
3.2 with whichever answer is reached - right now it still says "wait for
Phase 6" unconditionally, which this investigation suggests is not the whole
truth.
